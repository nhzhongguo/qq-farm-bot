# 项目升级分析报告

- 审计日期：2026-07-19
- 审计对象：QQ农场智能助手，主线 `main@3db5318`，当前发布版本 `2.3.2`
- 目标：定义一次可维护、可验证的商业级本地优先升级，不以框架重写或依赖升级制造表面变化。
- 方法：源码结构审查、测试与构建基线、临时隔离实例 UI 核验、现有功能审计复核，以及公开开源项目资料对照。

## 1. 产品与范围

本项目是本地优先的多账号 QQ 农场自动化控制台，核心价值是让用户安全地管理账号、策略、Worker 和长期运行状态。它不是通用工作流平台，也不是多租户云 SaaS。

因此，本次升级的正确方向是：把现有的“功能已经很多的自动化工具”提升为“任务可追踪、失败可诊断、配置可迁移、页面可高频使用、发布可验证”的控制台。以下内容不属于本次主线：分布式 Worker、拖拽式低代码画布、泛 AI 助手、无使用证据的微服务拆分，以及将 JSON 数据强行迁移为 PostgreSQL。

## 2. 审计基线

| 项目 | 结果 | 结论 |
| --- | --- | --- |
| Git | `main` 与 `origin/main` 一致，工作区干净 | 可作为升级基线 |
| 后端测试 | `pnpm test`，38/38 通过 | 数据安全、HTTP 安全、微信会话有回归保护 |
| 前端构建 | `pnpm build:web` 通过 | TypeScript 与生产构建可用 |
| 依赖审计 | `pnpm audit --prod` 无已知漏洞 | 不需要为安全目的盲目升级依赖 |
| 运行时版本 | 声明 pnpm `10.30.2`，本机 pnpm `11.9.0` | 需要 CI 固定工具链，但不可直接修改锁文件 |
| API | 92 个 HTTP 路由：34 GET、50 POST、8 DELETE | 覆盖广，但入口过度集中 |
| 数据 | JSON + 原子写入 + `.bak` 恢复 | 单机可靠性较好，缺少事务、迁移与跨进程锁 |

## 3. 当前项目优势

1. 业务闭环完整：账号、农场、好友、背包、奖励、策略、后台、卡密和推送均已落地，不是空壳面板。
2. 单账号 Worker、运行时管理器和调度器形成了多账号自动化基础；服务重启不会擅自拉起所有账号。
3. 数据安全优于普通个人项目：`users.json`、`cards.json`、`accounts.json` 已有原子写入、备份与损坏恢复；密码使用 PBKDF2 与常量时间比较。
4. 安全边界已具备：HTTP 安全头、公开路由白名单、登录/注册/卡密限流、首次管理员改密、会话绝对/空闲 TTL、同源 Socket 限制及微信密钥不回显。
5. 前端已经有 Vue 3、TypeScript、Pinia、路由级懒加载、主题 token、基础输入/按钮/空态/确认框/Toast，不应推倒重来。
6. 登录页已达到良好视觉起点：隔离实例的桌面与 390px 移动审查均显示清晰层级、可靠的输入状态和可读的版本信息。

## 4. 当前不足与架构问题

| 领域 | 证据 | 问题 | 2.0 处理方式 |
| --- | --- | --- | --- |
| HTTP 入口 | `core/src/controllers/admin.js` 约 2470 行、承载 92 路由 | 鉴权、输入处理、账号业务、后台业务和实时连接耦合，冲突率与测试成本高 | 先抽出路由注册与领域 handler，不改现有 URL 契约 |
| 配置模型 | `core/src/models/store.js` 约 1242 行 | 全局与账号策略、归一化、持久化混在一起，缺 schema version | 增加显式策略 schema、导入导出和校验层 |
| 数据层 | 同步 JSON 读写 | 适合单机，但多进程/多实例无法保证事务或并发写一致性 | 保持 JSON；为将来 SQLite 做 repository 边界，不在本次强迁移 |
| 自动化可观测性 | 调度快照是内存态 | 重启后不能还原任务执行、耗时、跳过和失败链路 | 持久化 task run、失败诊断包、告警规则 |
| 权限与审计 | 只有 `admin/user`，登录日志不等于操作审计 | 管理变更不可追溯，敏感操作复盘不足 | 先做不可篡改倾向的脱敏操作审计；RBAC 作为条件性下一步 |
| API 契约 | 92 路由集中，缺 OpenAPI 与统一输入 schema | 外部集成和前后端回归依赖人工记忆 | 先写高风险 API 契约与错误码文档，再渐进引入校验 helper |
| 质量门 | 主线无 CI；`lint` 脚本带 `--fix` | CI 无法纯检查，发布质量依赖人工 | 拆分 `lint:check`/`lint:fix`，接入 CI |

## 5. UI/UX 审计

### 已有优点

- 主题 token、明暗主题、路由进度、Toast、确认框和空状态已经形成基础设计系统。
- 路由使用动态 import，登录页在桌面/移动视口均没有文字溢出，首要操作可识别。
- 多数列表和异步操作已有 loading 或错误状态，好友头像使用延迟加载。

### 主要问题

1. 信息架构仍按源码模块排列，而不是按用户日常工作流排列：概览、调度、日志、告警、策略、账户运维之间缺少连续路径。
2. `AdminPanel.vue` 约 1610 行、`Settings.vue` 约 1495 行、`Friends.vue` 约 1142 行、`Sidebar.vue` 约 1033 行；页面状态、请求、展示和交互混杂，容易导致视觉调整牵动业务逻辑。
3. 组件有空态但没有统一 Skeleton、请求重试、离线恢复和页面级错误边界；用户在慢网络下会看到不一致的等待体验。
4. 可访问性只在少数控件上出现 `aria-*` 或键盘事件；模态焦点捕获、Select 键盘操作、图像替代文本和跳过导航尚未形成基线。
5. 响应式布局已经存在，但没有系统化移动端验收矩阵。登录页移动版可用，后台、设置、好友批量操作和调度页仍需真实窄屏核验。
6. 登录页的品牌首屏较完整，但登录后的运维界面需要更强的状态优先级：失败、即将执行、长时间无心跳、待处理账号应比一般卡片更醒目。

## 6. 性能与可靠性问题

1. 后端配置、用户、账号大量同步文件读写；数据量增长或同时大量管理操作时会阻塞事件循环。单机规模可接受，但应减少重复读取并把批量变更串行化。
2. 大型单文件页面导致更高的构建、类型检查和协作冲突成本。路由已懒加载，这是现有优势；下一步是按领域拆页面内部组合式逻辑，而不是额外引入状态库。
3. 调度器有超时保护，但没有统一的任务执行记录、超时、重试、退避和连续失败状态，无法针对慢任务建立可靠 SLO。
4. 日志可展示但缺少结构化查询、导出、关联 ID 与失败诊断包；实际故障处理需要手工拼接信息。
5. 版本和运行环境没有机器可读 manifest；pnpm 声明与实际环境不一致，且没有 CI 来阻断漂移。

## 7. 安全与可扩展性评估

当前基础安全已达到个人自托管的合理水平。仍需补齐：脱敏操作审计、静态敏感字段加密/轮换策略、配置导出脱敏、精细权限与 MFA 的条件性设计。公开部署前还应复核反向代理、HTTPS、备份演练和微信协议服务的供应链边界。

可扩展性应遵循单机优先：先让 JSON 上的数据模型、schema、审计和任务历史稳定；仅在确有多实例、多人协作或数据量瓶颈时，迁移到 SQLite，再考虑 PostgreSQL、队列和分布式 Worker。

## 8. 同类项目差距

| 对照对象 | 可借鉴能力 | 本项目差距 | 决策 |
| --- | --- | --- | --- |
| n8n | 凭据边界、模板、审计、RBAC、导入导出 | 配置不可迁移，管理操作不可追溯 | 吸收审计与策略包；不复制通用集成市场 |
| Kestra / Airflow | 执行历史、状态机、失败重试、超时、可观测性 | 任务运行只看当前快照 | 吸收 task run、失败策略和告警；不引入 DAG 引擎 |
| Node-RED | 可视化调试、配置导入导出、节点扩展 | 配置复用弱 | 先做 JSON 策略包与预览；不做拖拽画布 |
| AzurLaneAutoScript | 7x24 自动化、错误诊断资产 | 失败时缺一键复盘材料 | 吸收失败诊断包和错误分类 |
| uiautomator2 | 环境 doctor、明确诊断输出 | 只有基础 ping | 增加本机运行环境 doctor |

公开来源：GitHub `n8n-io/n8n`、`kestra-io/kestra`（2026-07-19 元数据核验），以及仓库已存证的 `docs/audit/sources/` 中 Airflow、Node-RED、ALAS、uiautomator2 公开资料快照（2026-07-15）。

## 9. 结论

项目不需要“换技术栈式升级”。建议将本次称为“商业级 2.0 产品升级”，语义化发布号从 `2.3.2` 升至 `2.4.0`；只有在引入不可兼容的数据迁移或 API 破坏时才升 `3.0.0`。主线应优先建设可靠性和可观测性，然后再做肉眼可见的控制台重组与微交互，而不是先堆叠动画。
